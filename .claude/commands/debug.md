# Debug — 문제 해결 전용

이 프로젝트는 **Debug 단계**다.

---

## 입력 인자

- `INPUT: $ARGUMENTS`
- 권장 호출:
  - `/debug 로그인 실패`
  - `/debug TASK-003 결제 API 500`
- 인자가 없으면 `[PROBLEM]` 블록 작성을 먼저 요청한다.

## 역할

- 문제 해결 전용
- 체계적 원인 분석
- 최소 침습적 해결

---

## 진단 트리 (Decision Tree)

```
문제 발생
├── 1. 에러 메시지가 있는가?
│   ├── YES → Step A: 에러 메시지 분석
│   └── NO → Step B: 증상 기반 분석
│
├── 2. 언제부터 발생했는가?
│   ├── 방금 코드 변경 후 → git diff 확인 → 최근 변경 롤백 테스트
│   ├── 갑자기 (코드 변경 없이) → 환경 문제 의심 → /devops-check
│   └── 처음부터 → 설정/의존성 문제
│
├── 3. 어디서 발생하는가?
│   ├── 빌드 시 → 의존성/설정 문제
│   ├── 런타임 시 → 로직/데이터 문제
│   ├── 특정 환경에서만 → 환경 차이 문제
│   └── 간헐적 → Race condition / Flaky 의심
│
└── 4. 범위는?
    ├── 한 파일/함수 → 로컬 디버깅
    ├── 여러 파일 → 인터페이스/데이터 흐름 추적
    └── 시스템 전체 → 환경 점검 우선
```

---

## 5단계 디버깅 프로세스

### Step 1: 문제 정의 (재현)

```
[PROBLEM]:
- 무엇이 문제인가: [증상 서술]
- 에러 메시지: [정확한 에러 텍스트]
- 재현 조건: [어떤 상황에서 발생하는가]
- 발생 빈도: [항상 / 간헐적 / 특정 조건]
- 최근 변경: [마지막으로 바꾼 것]
```

**필수:** 재현 가능한 최소 조건을 먼저 확보한다.

### Step 2: 가설 수립 (최대 3개)

```
[HYPOTHESES]:
1. [가설 A]: [근거] → 확인 방법: [구체적 명령/코드]
2. [가설 B]: [근거] → 확인 방법: [구체적 명령/코드]
3. [가설 C]: [근거] → 확인 방법: [구체적 명령/코드]
```

**규칙:** 가장 가능성 높은 가설부터 검증. 가설 3개 모두 실패하면 범위를 넓힌다.

### Step 3: 검증 (하나씩 순차)

```
[VERIFICATION]:
- 가설 A 검증: [실행한 명령] → 결과: [확인/반증]
- 가설 B 검증: [실행한 명령] → 결과: [확인/반증]
```

**금지:** 여러 가설을 동시에 수정하지 않는다. 한 번에 하나만 바꾼다.

### Step 4: 해결

```
[SOLUTION]:
- 즉시 조치: [무엇을 어떻게 변경]
- 변경 파일: [파일 경로]
- 변경 범위: [최소 수정만]
```

**규칙:**
- 최소 침습적 수정 (코드 1줄 바꿀 수 있으면 1줄만)
- 구조 변경은 최후 수단
- 수정 전 `git stash` 또는 브랜치 생성

### Step 5: 검증 & 재발 방지

```
[VERIFIED]:
- 재현 테스트: [문제가 해결되었는가]
- 사이드 이펙트: [다른 곳에 영향 없는가]
- 재발 방지: [테스트 추가 / 타입 강화 / 린트 규칙]
```

## 문제 유형별 빠른 참조

### 빌드 에러
```bash
# 의존성 문제
rm -rf node_modules && npm install
# 타입 에러
npx tsc --noEmit
# 설정 문제
cat tsconfig.json | head -20
```

### 런타임 에러
```bash
# 콘솔 로그 확인
# 네트워크 탭 확인
# 데이터 흐름 추적 (입력 → 처리 → 출력)
```

### 환경 문제
```
/devops-check 실행 또는:
1. scripts/doctor.sh 실행
2. Docker 상태 확인: docker ps
3. iCloud 경로 확인: pwd | grep -i icloud
4. 디스크 공간 확인: df -h
```

### 성능 문제
```
1. 브라우저 Performance 탭
2. 네트워크 요청 크기/시간 확인
3. 리렌더링 횟수 확인 (React DevTools)
4. 번들 크기 확인: npm run build -- --analyze
```

## 금지 사항

- ❌ 범위 확장 (버그 수정 중 리팩토링 금지)
- ❌ 여러 가설 동시 수정 (디버깅 통제 불가)
- ❌ 구조 변경 (최후 수단)
- ❌ 전체 재설치 (최후 수단)
- ❌ "잘 모르겠으니 전부 다시 만들자" (금지)

## 에스컬레이션

5단계 프로세스로 해결 안 되면:
1. **Healer Agent 호출** — 테스트 실패 자동 분석
2. **DevOps Guard 호출** — 환경 문제 진단
3. **playbook/09-routines-guides/common-mistakes-and-recovery.md** 참조

## 핵심 원칙

**문제의 90%는 작업 방식 문제다.**

구조 변경 전에 작업 방식부터 점검한다.
한 번에 하나만 바꾸고, 바꾼 것을 검증한다.

# Non-Developer UX Interpretation Layer

> 기술 태그를 비개발자가 이해할 수 있는 해석으로 변환하는 규칙
>
> **SSOT (Single Source of Truth):** 모든 IDE가 이 규칙을 참조하여 구현
> **작성일:** 2026-02-22
> **버전:** 1.0

---

## 🎯 목표

```
기술 에이전트의 [GATE], [JUDGMENT], [ITERATION_SCOPE] 출력을
비기술 사용자(CEO, PM, 비개발자)가 다음 액션을 명확하게 이해할 수 있도록 변환
```

---

## 📐 3-Layer 해석 구조

### Layer 1: 기술 태그 (AI 자동 생성)
```
[GATE]: OPEN/HOLD
[VALUE]: PASS/HOLD
[RESOURCE]: PASS/HOLD
[HUMAN_OVERRIDE]: ACCEPTED/ACCEPTED_MANUAL/REJECTED/N/A
[REASON]: 기술적 근거
```

### Layer 2: 인간 해석 (이 문서에서 정의)
```
현재 상태 → 사람이 이해할 수 있는 상태 설명
다음 단계 → 구체적인 다음 액션
필요한 것 → 무엇이 필요한가
기대값 → 언제쯤 완료될 것 같은가
```

### Layer 3: 구체적 가이드 (단계별)
```
실행 방법 → 구체적 HOW
연락처 → 누가 담당하는가
예상 투자 → 비용/시간/인원
성공 신호 → 무엇이 성공인가
```

## 🔄 Phase별 해석 규칙

### Phase 2: Decision 판정 → "지금 진행해야 할까?"

**Layer 1 (기술):**
```
[JUDGMENT]: 계속 / 종료 / 보류 / 피벗
[HUMAN_OVERRIDE]: ACCEPTED / REJECTED / N/A
[REASON]: <데이터 기반 근거>
```

**Layer 2 (인간 해석):**
```
상황: 사업 아이디어에 대한 최종 판정

현재 상태:
- "당신의 아이디어 분석이 완료되었습니다"
- "시장 조사와 실행 가능성이 검토되었습니다"

다음 단계:
- "계속": 즉시 개발에 들어갈 수 있습니다
- "보류": 추가 정보/검증이 필요합니다
- "종료": 지금 이 아이디어는 추천하지 않습니다

필요한 것:
- "계속" 판정 시: 팀 구성, 자본금, 시간 배분
- "보류" 판정 시: 추가 시장 조사, 고객 인터뷰
- "종료" 판정 시: 아이디어 재검토 또는 새 아이디어

기대값:
- 평균 의사결정 시간: 2-3일
- 비용: 없음 (분석은 AI가 수행)
```

**Layer 3 (구체적 가이드):**
```
다음 할 일:

[ ] 1단계: 판정 결과 팀과 공유 (30분)
   연락처: CEO/PM
   방법: 디스코드/슬랙 채널에 결과 공유

[ ] 2단계: "계속" 판정인 경우 아래 진행
   2-1. 팀 구성 회의 (1시간)
       필요한 역할: 개발자, 디자이너, CS/PM
   2-2. 예산 확인 (1일)
       예상 비용: [아이디어별로 제시]
   2-3. 첫 2주 스프린트 계획 (2시간)

[ ] 3단계: "보류/종료" 판정인 경우
   피드백 검토 (30분)
   대체 아이디어 논의 (1시간)
   재도전 일정 수립

성공 신호:
- 팀이 판정을 이해하고 동의했다
- 다음 단계 스케줄이 정해졌다
- 필요한 리소스 할당이 명확하다
```

### Phase 3: Execution Gate → "정말 가능할까?"

**Layer 1 (기술):**
```
[GATE]: OPEN / HOLD
[VALUE]: PASS / HOLD
[RESOURCE]: PASS / HOLD
```

**Layer 2 (인간 해석):**
```
상황: 실제 개발 시작 전 최종 검증

현재 상태:
- "[GATE]: OPEN" = 개발 시작 OK
- "[GATE]: HOLD" = 아직 준비 안 됨

상세:
- [VALUE] PASS: 사업적 가치가 확인됨
- [VALUE] HOLD: 시장 검증이 더 필요함
- [RESOURCE] PASS: 필요한 인력/비용이 확보됨
- [RESOURCE] HOLD: 팀/자본 보충이 필요함

필요한 것:
- OPEN인 경우: 개발 팀을 배치하고 스프린트 시작
- HOLD인 경우: 부족한 부분 채운 후 재검증

기대값:
- OPEN: 2주 내 MVP 개발 시작 가능
- HOLD: 1-2주 내 보충 후 재검증
```

**Layer 3 (구체적 가이드):**
```
[ ] Action 1: Gate 결과 확인 (즉시)
    ✅ OPEN이면: 다음으로
    ⏸️ HOLD이면: "부족한 리소스" 섹션 확인

[ ] Action 2: 개발 팀 배치 (1일)
    팀 구성:
    - 백엔드 개발자 1-2명
    - 프론트엔드 개발자 1-2명
    - 디자이너 1명 (겸임 가능)
    - QA/테스터 1명

    배치 방법:
    - 내부 팀 일정 조율
    - 외부 개발사 계약 (필요 시)

[ ] Action 3: 스프린트 계획 회의 (3시간)
    아젠다:
    - 기술 스택 최종 확정
    - 첫 2주 MVP 기능 정의
    - 일일 스탠드업 시간 정하기
    - 문제 발생 시 연락 체계

[ ] Action 4: 개발 환경 준비 (1일)
    - 리포지토리 생성
    - CI/CD 파이프라인 설정
    - 개발 서버 구성

성공 신호:
- 팀이 확정되고 배치되었다
- 스프린트 계획이 정해졌다
- 첫 코드 커밋이 진행 중이다
```

### Phase 4-5: 개발 중 피드백 → "진행 상황이 어때?"

**Layer 1 (기술):**
```
[ITERATION_SCOPE]: DRAFT / NEED_INPUT
[REASON]: 현재 기술적 상태
```

**Layer 2 (인간 해석):**
```
상황: 개발 진행 중 매주 검토

현재 상태:
- DRAFT: 예정대로 진행 중
- NEED_INPUT: 의사결정/피드백 필요

상세:
- DRAFT: 개발 팀이 자율적으로 진행 중, 다음 주 검토
- NEED_INPUT: 기술 선택, 기능 우선순위, 디자인 결정 등에서 피드백 필요

필요한 것:
- DRAFT: 현상 유지, 정기 체크인만
- NEED_INPUT: PM/경영진의 즉각적 의견 제출

기대값:
- DRAFT: 예정대로 2주 내 완료
- NEED_INPUT: 피드백 24시간 내 필요 (최대 48시간)
```

**Layer 3 (구체적 가이드):**
```
[ ] 매주 월요일: 스프린트 리뷰 회의 (1시간)
    참석자: PM, 기술 리더, 개발팀 대표
    아젠다:
    - 지난주 완료 기능 확인
    - 이번주 계획된 기능 확인
    - 문제점/블로커 논의
    - 우선순위 재조정 (필요시)

[ ] NEED_INPUT 발생 시:
    1. 의사결정 항목 명확히 정의 (개발팀이 제시)
    2. PM/경영진 피드백 수집 (24시간 내)
    3. 개발팀에 즉시 전달
    4. 개발 재개

성공 신호:
- 매주 계획한 기능의 80% 이상 완료됨
- 블로커가 24시간 내에 해결됨
- 팀의 사기가 유지되고 있음
```

### Phase 6-7: 배포 전 검증 → "출시 가능한가?"

**Layer 1 (기술):**
```
[GATE]: OPEN / HOLD
[VALUE]: PASS / HOLD
[RESOURCE]: PASS / HOLD
```

**Layer 2 (인간 해석):**
```
상황: 개발 완료 후 배포 가능성 최종 검증

현재 상태:
- OPEN: 배포 준비 완료
- HOLD: 아직 준비 안 됨

평가 항목:
- [VALUE] PASS: 기능이 완성되었다
- [RESOURCE] PASS: 배포/운영 인력이 준비됐다
- 성능: 안정적인가?
- 보안: 안전한가?
- 사용성: 사용자가 쉽게 쓸 수 있는가?

필요한 것:
- OPEN인 경우: 배포 진행
- HOLD인 경우: 지적된 항목 수정 후 재검증

기대값:
- OPEN: 이번 주 배포 진행 (Staging → Beta → Production)
- HOLD: 1-2주 내 수정 후 재검증
```

**Layer 3 (구체적 가이드):**
```
Checklist: 배포 전 필수 확인 사항

[ ] 기능 완성도 (개발팀 확인)
    - 모든 MVP 기능 구현됨
    - 기본 테스트 통과 (자동 테스트 80% 이상)
    - 주요 버그 없음

[ ] 성능 테스트 (QA팀 확인)
    - 응답 시간 < 1초
    - 동시 사용자 1,000명 대응 가능
    - 메모리/CPU 정상 범위

[ ] 보안 검증 (보안팀 또는 외부 컨설턴트)
    - 로그인/인증 안전
    - 데이터 암호화됨
    - SQL injection 등 취약점 없음

[ ] 사용성 테스트 (실제 사용자 5-10명)
    - 첫 사용 시간 < 5분
    - 기본 기능 직관적
    - 헷갈리는 부분이 없는가?

[ ] 배포 계획 수립 (운영팀)
    - Staging 배포: 내부 테스트 3일
    - Beta 배포: 제한 사용자 1주
    - Production 배포: 정식 운영 시작

배포 진행 (OPEN 판정 시):
1. Staging 배포 (Day 1)
2. 내부 테스트 (Day 1-3)
3. Bug fix 및 재테스트 (Day 3-4)
4. Beta 배포 (Day 5-12)
5. Beta 피드백 수집 및 반영 (Day 5-12)
6. Production 배포 (Day 13)
7. 모니터링 24/7 (2주)

성공 신호:
- 배포가 완료됨
- 99.9% 서비스 가용성 유지
- 사용자 피드백이 긍정적
```

### Phase 8: 운영 자동화 → "앞으로 어떻게 운영하지?"

**Layer 1 (기술):**
```
[OPERATIONS_PLAN]
- 자동화 규칙 정의
- 모니터링 지표
- 알림 설정
```

**Layer 2 (인간 해석):**
```
상황: 서비스 라이브 후 일상적 운영

현재 상태: 서비스가 운영 중임

운영 방식:
- 자동: AI가 자동으로 감시하고 대응
- 수동: 사람이 확인하고 결정
- 혼합: 자동 감시 + 사람 최종 검토

필요한 것:
- 운영 담당자 (1-2명)
- 모니터링 대시보드
- 알림 설정
- 매주 성과 리뷰

기대값:
- 99.9% 가용성 유지
- 버그 발생 시 1시간 내 감지
- 중요 이슈 4시간 내 해결
```

**Layer 3 (구체적 가이드):**
```
일일 운영 (자동화)

[ ] 08:00 - 자동 헬스체크
    시스템이 자동으로:
    - 서버 상태 확인
    - 데이터베이스 백업 확인
    - 에러 로그 집계
    결과: 이상 없으면 통보 없음, 있으면 알림

[ ] 12:00 - 사용 현황 리포트
    자동 생성:
    - 일일 활성 사용자 수
    - 주요 기능 사용률
    - 에러율
    담당자에게 이메일 발송

[ ] 18:00 - 성능 리포트
    자동으로:
    - 서버 응답 시간 추적
    - 에러 레이트 추적
    - 리소스 사용량 추적
    이상 시 즉시 알림

주간 운영 (수동)

[ ] 매주 월요일 09:00 - 주간 성과 리뷰 (1시간)
    참석: 운영팀 + PM
    검토 항목:
    - 지난주 KPI (사용자 수, 에러율, 만족도)
    - 이번주 계획
    - 개선 사항

[ ] 필요 시 - 버그 대응
    발생 → 자동 감지 (AI) → 담당자 알림 → 개발팀 대응
    목표: 심각한 버그 4시간 내 패치

[ ] 월 1회 - 용량 계획 검토
    예상 사용자 증가량 분석
    필요한 서버 증설 계획

성공 신호:
- 99.9% 이상 가용성 유지
- 사용자 만족도 NPS > 40
- 월간 활성 사용자 증가율 15% 이상
```
